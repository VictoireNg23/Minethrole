# SIGSYS 435 confirmé : compatibilité clone3 sans autoriser clone3

La capture GDB utilisateur identifie SIGSYS, si_code=1, syscall=435, architecture `0xc000003e` (x86-64), orig_rax=435, dans pthread_create au démarrage du renderer. Il s'agit de clone3, utilisé par la glibc récente de l'hôte. Le filtre historique provoque SIGSYS au lieu de laisser la glibc utiliser son repli sur clone.

L'adaptation séparée `patches/chromium71/glibc-clone3-enosys.patch` renvoie uniquement ENOSYS pour le numéro 435 sur x86-64 hors ABI x32, dans la baseline seccomp. Elle **n'autorise pas clone3** ; le chemin clone existant et ses restrictions d'arguments restent inchangés. La plage des syscalls x86-64 de cette révision va déjà jusqu'à 1024 : aucune extension de plage ni changement global d'InvalidSyscall n'est nécessaire. La baseline est partagée par plusieurs politiques, donc ce résultat ENOSYS vaut aussi pour les autres processus qui héritent de cette branche, pas seulement le renderer.

Un test BPF natif ajouté à baseline_policy_unittest.cc exige retour -1/errno ENOSYS pour syscall 435, y compris sur un noyau qui ne l'implémente pas. Le test CreateThread existant et les tests de restrictions clone doivent aussi être exécutés après compilation. Ce test natif n'a pas été compilé ou exécuté dans Codex ; les tests Python vérifient seulement la portée du patch. Les fichiers historiques exacts ont été relus pour préparer les contextes, sans téléchargement d'un arbre ou build Chromium dans Codex.

Le script d'application vérifie le HEAD Chromium et le SHA-256 de l'adaptation, exige les deux fichiers ciblés inchangés, sauvegarde leurs contenus puis applique après git apply --check. Il ne change aucun patch original MineThrottle ni compteur, signature, profil, formule ou seuil. Aucune compilation ni modification du sandbox d'un processus actif n'est effectuée à cette étape.

Après retour d'application, recompiler Chromium et le binaire de tests sandbox, exécuter les tests natifs ciblés puis préparer une nouvelle copie de navigateur avec sa nouvelle empreinte. Le staging précédent reste conservé : il contient encore l'ancien binaire, et ne doit pas être déclaré corrigé par la seule modification des sources. Ensuite retester la page bénigne sans pause de debugger, en exigeant toujours renderer non root, Seccomp=2 et NoNewPrivs=1. Aucune exécution du dataset n'est encore effectuée.
