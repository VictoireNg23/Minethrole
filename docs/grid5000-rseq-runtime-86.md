# Deuxième SIGSYS : rseq 334 ; tester la désactivation glibc locale

La capture `raw/sandbox-native-78__1726/result.json` identifie SIGSYS, syscall 334, architecture x86-64, dans le nouveau thread après clone. Il s'agit de rseq (restartable sequences), enregistré par la glibc récente. L'adaptation clone3 ENOSYS a permis d'atteindre cette étape ; son succès ne suffisait pas à assurer la création complète d'un thread. Le code 0 de GDB n'est pas une réussite du test ; l'absence de XML complet reste diagnostique.

La prochaine tentative conserve le filtre sandbox et la politique rseq d'origine. Le flag `--disable-glibc-rseq` fixe `GLIBC_TUNABLES=glibc.pthread.rseq=0` pour le processus de test et ses descendants, avant l'initialisation de la glibc. Cette option désactive son optimisation facultative rseq, sans autoriser le syscall dans seccomp. Elle n'est appliquée ni au système global ni aux autres sessions. Les autres tunables glibc existants sont conservés ; les valeurs précédentes du seul réglage rseq sont remplacées dans cet environnement de test.

Le réglage doit être appliqué dès le lancement du processus, pas seulement après installation du sandbox : une glibc ayant déjà enregistré rseq dans le thread initial peut traiter un échec ultérieur comme fatal. Les rapports enregistrent la valeur effective transmise et le fait qu'elle est demandée par le contrôleur. Le succès est à établir par les trois tests BPF normaux, pas par une nouvelle capture GDB seule.

Il s'agit d'une adaptation d'environnement liée à glibc 2.35, pas d'un changement de signatures, compteurs ou règles MineThrottle. Désactiver rseq peut influer sur les performances de l'hôte ; conserver cette configuration dans toutes les comparaisons et ne pas présenter les vitesses mesurées comme identiques à l'environnement original des auteurs. L'effet et la compatibilité avec les profils restent à évaluer. Si les tests réussissent, le navigateur devra être lancé avec ce même environnement local avant le test synthétique.
